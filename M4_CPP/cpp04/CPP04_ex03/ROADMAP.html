Phase 1 · 20 min

L'histoire et la carte

Le sujet vient du jeu Final Fantasy VII. Une Materia est une petite boule magique. On la range dans l'équipement d'un personnage, et elle lui donne un sort.

AMateria

Un sort « en général ». Il n'existe jamais tout seul, on a toujours un sort précis. Donc la classe est abstraite.

Ice et Cure

Deux sorts précis. Ice attaque (« shoots an ice bolt »). Cure soigne (« heals … wounds »).

Character

Un héros avec un sac de 4 emplacements. Il équipe des Materias, les pose par terre, et les lance sur une cible.

MateriaSource

Un livre de recettes. Il apprend jusqu'à 4 modèles de sorts. Ensuite, on lui dit « fais-moi un ice » et il fabrique une copie neuve.

Derrière l'histoire, le sujet teste 3 choses :

  • Copier un objet sans connaître son vrai type. C'est le rôle de clone().
  • Écrire et utiliser des interfaces : ICharacter et IMateriaSource.
  • Savoir qui doit faire le delete de chaque objet. C'est là que les fuites mémoire arrivent.

Le rôle des 7 classes

Le rôle, c'est à quoi sert la classe dans le programme, en une phrase. C'est ce que tu dirais pour la présenter au correcteur.

Le main du sujet, lu comme une histoire

Ce main est le premier test que le correcteur lancera. On le lit bloc par bloc. La version annotée ligne par ligne est à la fin de la page.

Bloc 1. On crée le livre de recettes

IMateriaSource* src = new MateriaSource();
src->learnMateria(new Ice());
src->learnMateria(new Cure());

La 1re ligne a 3 morceaux :

IMateriaSource*    src    =    new MateriaSource();
  (1) l'étiquette  (2) le nom     (3) le vrai objet
  • (1) IMateriaSource* : le genre de chose qu'on tient, « un livre de recettes, n'importe lequel ». C'est le contrat.
  • (2) src : le nom de la variable, pour « source ». Tu pourrais l'appeler livre.
  • (3) new MateriaSource() : le vrai livre, créé vide en mémoire.

C'est la même idée que const AAnimal* j = new Dog(); dans ton ex02 : l'étiquette dit « animal », le vrai objet est un Dog.

Les 2 lignes suivantes apprennent 2 modèles au livre : un Ice et un Cure.

ces 2 objets appartiennent maintenant au livre. C'est lui qui devra les delete.

Bloc 2. On crée un héros et on lui donne des sorts

ICharacter* me = new Character("me");

AMateria* tmp;
tmp = src->createMateria("ice");
me->equip(tmp);
tmp = src->createMateria("cure");
me->equip(tmp);
  • On crée un héros appelé « me », avec un sac vide.
  • createMateria("ice") : le livre cherche son modèle « ice » et renvoie une copie neuve, grâce à clone().
  • tmp est juste une main qui tient la Materia une seconde, le temps de la donner au héros.
  • equip(tmp) : le héros la range dans le slot 0. Puis Cure va dans le slot 1.

ces 2 copies appartiennent maintenant au héros. C'est lui qui devra les delete.

Bloc 3. On crée une cible et on lance les sorts

ICharacter* bob = new Character("bob");

me->use(0, *bob);
me->use(1, *bob);
  • On crée un 2ᵉ personnage, « bob ». Il sert juste de cible.
  • use(0, *bob) : « me » lance le sort du slot 0 (Ice) sur bob.
  • use(1, *bob) : il lance le sort du slot 1 (Cure) sur bob.
  • *bob veut dire « l'objet bob lui-même », pas son adresse. C'est parce que use attend une référence (ICharacter&).

Résultat attendu. Avec | cat -e, le $ marque la fin de chaque ligne :

* shoots an ice bolt at bob *$
* heals bob's wounds *$

Bloc 4. On range tout

delete bob;
delete me;
delete src;
  • delete me : son destructeur doit supprimer les Materias de son sac.
  • delete src : son destructeur doit supprimer ses modèles.

si chaque destructeur fait bien son travail, valgrind affiche zéro fuite.

Pourquoi ICharacter* et pas Character* ?

Le main ne connaît que les interfaces. Il sait ce qu'un personnage peut faire, pas comment c'est codé. C'est exactement le but de l'exo.

Question de vérif : à la fin du bloc 2, combien d'objets possède « me », et qui les a fabriqués ?
2 Materias : un Ice dans le slot 0 et un Cure dans le slot 1. Ce sont des copies fabriquées par le livre (createMateria, qui appelle clone()).

Phase 3 · 2 h

Les notions à connaître

D'abord 6 bases du C++ qui servent partout. Ensuite 8 notions propres à ce module. Lis-en une, réponds à sa question de vérif, puis passe à la suivante.

A. Les bases du C++ utiles ici

A1Le .hpp et le .cpp

Chaque classe est en général coupée en 2 fichiers :

  • .hpp = la carte d'identité (on dit aussi fichier d'en-tête). Il dit ce que la classe a : ses attributs et la liste de ses fonctions. C'est la déclaration.
  • .cpp = le travail (on dit aussi fichier source). Il dit comment chaque fonction marche. C'est la définition.

Exemple avec getType() de l'exercice :

// AMateria.hpp : la déclaration
class AMateria {
    protected:
        std::string _type;
    public:
        std::string const & getType() const;   // juste la signature, avec un ;
};

// AMateria.cpp : la définition
#include "AMateria.hpp"
std::string const & AMateria::getType() const {   // AMateria:: = "la fonction de la classe AMateria"
    return _type;
}

Une classe sans aucun code à écrire n'a besoin que d'un .hpp. C'est le cas des interfaces (voir B3). Toutes les autres classes ont un .hpp et un .cpp.

écrire le corps d'une fonction dans un .hpp (sauf les {} imposés dans les 2 interfaces du sujet).

Question de vérif : MateriaSource a-t-elle besoin d'un .hpp, d'un .cpp, ou des deux ?
Des deux. C'est une classe concrète : son .hpp déclare ses attributs et ses fonctions, son .cpp écrit le code de learnMateria, createMateria, etc.

A2Les gardes d'inclusion

Chaque .hpp commence et finit comme ça :

#ifndef ICE_HPP
# define ICE_HPP
// ... le contenu ...
#endif

Ça veut dire : « si ce fichier a déjà été lu, ne le relis pas ».

dans l'ex03, beaucoup de fichiers s'incluent entre eux. Sans gardes, une classe serait déclarée 2 fois : erreur de compilation.

Question de vérif : que se passe-t-il si Ice.hpp et Cure.hpp incluent tous les deux AMateria.hpp, sans gardes ?
Si le main inclut Ice.hpp et Cure.hpp, la classe AMateria est lue deux fois : erreur « redefinition of class AMateria ». Avec les gardes, la 2ᵉ lecture est sautée.

A3La forme canonique et la règle des trois

À 42, chaque classe concrète ou abstraite doit avoir ces 4 fonctions :

  1. un constructeur par défaut ;
  2. un constructeur de copie ;
  3. un opérateur d'affectation operator= ;
  4. un destructeur.

Ici : AMateria, Ice, Cure, Character et MateriaSource. Les interfaces sont recopiées telles quelles depuis le sujet : on n'y ajoute rien.

La règle des trois (les pros en parlent) : si une classe possède de la mémoire créée avec new, son destructeur, son constructeur de copie et son operator= doivent tous les trois s'en occuper. C'est le cas de Character et MateriaSource.

fais le destructeur virtual dans toute classe mère. Sinon, un delete via un pointeur de la mère n'appelle pas le destructeur de la fille.

Question de vérif : pourquoi Ice n'a pas besoin de la règle des trois, alors que Character oui ?
Ice ne possède aucun objet créé avec new (juste un texte). Character possède 4 Materias créées avec new : il doit les copier et les libérer lui-même.

A4Le mot const

std::string const & getType() const;
  • Le const du début (std::string const &) : on renvoie le texte en lecture seule, sans le copier.
  • Le const de la fin : cette fonction promet de ne rien modifier dans l'objet.

Mets const partout où c'est possible : une fonction qui ne fait que lire (getType, getName, clone) doit l'avoir.

le const de la fin fait partie du « nom complet » de la fonction. Si tu l'oublies dans une classe fille, ce n'est plus la même fonction (voir B1).

Question de vérif : pourquoi clone() est const ?
Parce que se photocopier ne modifie pas l'original. clone() lit l'objet et en crée un nouveau, sans toucher à lui-même.

A5NULL et le tableau de pointeurs

Le sac du héros est un tableau de 4 pointeurs. Chaque case contient une adresse, ou NULL si elle est vide.

AMateria* _inventory[4];
  • En C++98, on écrit NULL (nullptr n'existe pas encore).
  • Au départ, les cases contiennent n'importe quoi. Il faut les mettre à NULL dans le constructeur, avec une boucle.
  • Pour savoir si une case est vide : if (_inventory[i] == NULL).

delete NULL; ne fait rien et ne plante pas. Tu peux donc faire delete sur les 4 cases sans tester si elles sont vides.

Question de vérif : que se passe-t-il si tu oublies de mettre les cases à NULL dans le constructeur ?
Elles contiennent des adresses au hasard. equip croira que le sac est plein, et le destructeur fera delete sur des adresses au hasard : crash.

A6L'objet ou son adresse : avec ou sans *

  • IMateriaSource src; = créer un objet de ce type. ❌ Ne compile pas : une interface ne peut pas être créée.
  • IMateriaSource* src; = une variable qui contient l'adresse d'un objet. ✅ On y met l'adresse d'un vrai livre : src = new MateriaSource();

Image : sans *, c'est la maison. Avec *, c'est un papier avec l'adresse de la maison.

Character me("me");Character* me = new Character("me");

Appeler une fonctionme.equip(...) (point)me->equip(...) (flèche)

le pointeur est la seule façon de tenir un objet via son interface (ICharacter*) ou sa classe abstraite (AMateria*). C'est ce qui permet le polymorphisme.

Question de vérif : dans le main, pourquoi écrit-on me->use(...) et pas me.use(...) ?
Parce que me est un pointeur (ICharacter*). La flèche veut dire « va à l'adresse, puis appelle la fonction ».

B. Les notions du module

B1virtual et la redéfinition (rappel ex00)

Une fonction virtual dans la mère peut être redéfinie dans la fille. Avec un pointeur de la mère, le programme appelle la version de la fille. C'est le polymorphisme.

Pour redéfinir, la fille redéclare la fonction avec exactement la même signature : même nom, mêmes paramètres, même const.

// dans AMateria.hpp : virtual void use(ICharacter& target);
// dans Ice.hpp :      void use(ICharacter& target);   ← identique

Dans l'exo : le slot du sac est un AMateria*. Pourtant, _inventory[0]->use(bob) appelle Ice::use, car l'objet est vraiment un Ice.

une petite différence (un const en trop ou en moins, un & oublié) crée une nouvelle fonction au lieu de remplacer l'ancienne.

Question de vérif : si use n'était pas virtual dans AMateria, que ferait _inventory[0]->use(bob) ?
Il appellerait AMateria::use, qui ne fait rien. Rien ne s'afficherait, car le programme regarderait le type du pointeur (AMateria) au lieu du vrai objet (Ice).

B2La classe abstraite (rappel ex02)

Une classe avec au moins une fonction = 0 est abstraite. On ne peut pas la créer seule. Elle peut avoir des attributs et du code normal.

Ici, AMateria est abstraite grâce à clone() const = 0. Elle garde un attribut protected pour le type : la fiche d'évaluation le vérifie.

protected veut dire : invisible depuis le main, mais visible depuis les filles (Ice et Cure).

on ne doit jamais pouvoir créer une Materia « générique », seulement un Ice ou un Cure.

Question de vérif : AMateria a un .cpp. Pourquoi, alors qu'elle est abstraite ?
Parce qu'elle a du vrai code : ses constructeurs, getType(), use(), son destructeur. Seule clone() n'a pas de code (elle est = 0).

B3L'interface

Le C++ n'a pas de mot-clé « interface ». On appelle interface une classe qui ne contient que :

  • des fonctions virtuelles pures (= 0) ;
  • un destructeur virtuel.

Pas d'attribut. Pas de constructeur. Pas de code. Le préfixe I veut dire Interface.

Exemple : l'interface ICharacter du sujet.

class ICharacter {
    public:
        virtual ~ICharacter() {}                              // { } = corps vide, imposé par le sujet
        virtual std::string const & getName() const = 0;     // pure : pas de corps
        virtual void equip(AMateria* m) = 0;
        virtual void unequip(int idx) = 0;
        virtual void use(int idx, ICharacter& target) = 0;
};

Pourquoi pas de .cpp ? Les fonctions = 0 n'ont pas de code. Le destructeur a déjà son corps {} dans le .hpp. Il ne reste rien à écrire. Donc ICharacter et IMateriaSource n'ont qu'un .hpp.

« Implémenter une interface » veut dire : hériter d'elle avec public, et écrire toutes ses fonctions = 0.

class Character : public ICharacter {
    public:
        std::string const & getName() const;   // même signature, sans = 0
        void equip(AMateria* m);
        void unequip(int idx);
        void use(int idx, ICharacter& target);
        // déclarées dans Character.hpp, écrites dans Character.cpp
};

À quoi sert une interface, si on réécrit tout dans la classe concrète ?

  • C'est un contrat : si MateriaSource oublie createMateria, ça ne compile pas.
  • Celui qui l'utilise ne dépend que du contrat. Le main ne parle que d'IMateriaSource. Pour changer de livre un jour, on changerait une seule ligne.
  • Ice::use(ICharacter& target) peut viser n'importe quel personnage, sans le connaître. Il appelle juste target.getName().

Image : la prise électrique (l'interface) accepte n'importe quel appareil (classe concrète) qui a la bonne forme.

Question de vérif : Character peut-il oublier d'écrire unequip ?
Non. unequip est = 0 dans ICharacter. Si Character ne l'écrit pas, Character reste abstraite et new Character("me") ne compile plus (erreur « abstract type »).

B4clone() : la photocopieuse

Tu as un AMateria* dans la main. Tu veux une copie. Mais toi, tu ne sais pas si c'est un Ice ou un Cure.

  • new AMateria(*m) : impossible, AMateria est abstraite.
  • new Ice(*m) : faux si c'est un Cure.

Solution : on demande à l'objet de se copier lui-même. Lui connaît son vrai type. Grâce à virtual, m->clone() appelle la bonne version.

MateriaSource s'en sert pour fabriquer des sorts à partir de ses modèles. Character s'en sert pour la copie profonde de son sac.

clone() fait un new. Donc quelqu'un devra faire le delete correspondant.

Question de vérif : pourquoi clone() est = 0 dans AMateria ?
Parce qu'AMateria ne sait pas quel objet fabriquer : elle ne connaît pas le vrai type. Seuls Ice et Cure le savent. Donc chaque fille doit écrire sa propre version.

B6La copie profonde (rappel ex01)

Copier un Character, ce n'est pas copier les 4 adresses. Sinon, deux héros partagent les mêmes Materias.

Dans operator=, le sujet impose cet ordre :

  1. supprimer les Materias que j'ai déjà ;
  2. cloner chaque Materia de l'autre.

même idée que le Brain, mais avec clone(), car on ne connaît pas le type des Materias.

Question de vérif : je copie un Character, puis je détruis l'original. La copie marche-t-elle encore ?
Oui, si la copie est profonde : la copie a ses propres Materias (clonées), à d'autres adresses. Détruire l'original ne touche pas à ses objets à elle. Avec une copie superficielle, la copie pointerait vers des Materias déjà détruites.

Question de vérif : pourquoi unequip ne fait pas delete ?
Le sujet l'interdit : déséquiper, c'est poser la Materia par terre, pas la détruire. Elle existe toujours en mémoire. C'est au main (qui a gardé son adresse) de la libérer.

B8La composition : « posséder » des objets

Hériter, c'est « être » : un Ice est une AMateria. Composer, c'est « avoir » : un Character a 4 Materias dans son sac.

  • class Ice : public AMateria → héritage (« est un »).
  • AMateria* _inventory[4]; dans Character → composition (« a des »).

quand une classe possède des objets créés avec new, elle en est responsable : elle les copie (copie profonde) et les détruit (destructeur). C'est la règle des trois (A3).

Question de vérif : MateriaSource est-ce de l'héritage ou de la composition ?
Les deux. Elle hérite d'IMateriaSource (elle « est un » livre de recettes) et elle a 4 modèles dans _templates (composition).

Fiche de soutenance

Les questions que le correcteur peut te poser. Pour chacune : une réponse courte, avec un exemple de l'exercice.

C'est quoi une classe abstraite ?

Une classe avec au moins une fonction virtuelle pure (= 0). On ne peut pas la créer seule, seulement ses filles. Elle peut avoir des attributs et du code.

class AMateria {
    protected:
        std::string _type;                   // elle a un attribut
    public:
        virtual AMateria* clone() const = 0; // = 0 → abstraite
};
// new AMateria("ice");  ← ne compile pas
// new Ice();            ← OK

C'est quoi une interface ?

Une classe abstraite « pure » : que des fonctions = 0 et un destructeur virtuel. Pas d'attribut, pas de code. C'est un contrat : « toute classe qui hérite de moi a ces fonctions ».

Dans l'exo : ICharacter et IMateriaSource. Elles n'ont qu'un .hpp, car il n'y a aucun code à écrire.

À quoi sert une interface, si on réécrit tout dans la classe concrète ?

  • C'est un contrat qui impose une trame. Si MateriaSource oublie createMateria, ça ne compile pas.
  • Celui qui l'utilise ne dépend que du contrat. Le main ne parle que d'IMateriaSource. Pour changer de livre, on changerait une seule ligne.
  • Ice::use(ICharacter& target) peut viser n'importe quel personnage, sans le connaître.

Quelle différence entre classe abstraite et interface ?

AMateria a un attribut (_type) et du code (getType), donc un .cpp. ICharacter n'a rien de tout ça : seulement des = 0, donc un .hpp seul.

Que veut dire = 0 ?

La fonction est virtuelle pure : elle n'a pas de code dans la mère. Chaque fille doit l'écrire, sinon la fille est abstraite elle aussi.

Exemple : clone() est = 0 dans AMateria. Ice et Cure écrivent chacun leur version.

À quoi sert clone() ?

À copier une Materia sans savoir si c'est un Ice ou un Cure. On demande à l'objet de se copier lui-même, car lui connaît son vrai type.

Exemple : createMateria("ice") renvoie _templates[i]->clone(). Et la copie d'un Character clone chaque Materia de son sac.

Où est le polymorphisme ?

Dans me->use(0, *bob), me est un ICharacter*, mais c'est Character::use qui tourne. Puis _inventory[0]->use(bob) appelle Ice::use, alors que le slot est un AMateria*.

Pourquoi le destructeur est virtual ?

Dans le main, delete me; passe par un ICharacter*. Sans virtual, le destructeur de Character ne serait pas appelé, et ses Materias ne seraient jamais libérées : fuite. Pareil pour delete d'un AMateria* qui est un Ice.

Comment est faite la copie d'un Character ?

Copie profonde : je supprime mes Materias, puis je clone chaque Materia de l'autre. Les deux héros ont des Materias à des adresses différentes. Sinon, le même objet serait libéré deux fois.

C'est quoi la règle des trois ?

Si une classe possède de la mémoire créée avec new, son destructeur, son constructeur de copie et son operator= doivent tous les trois s'en occuper. Dans l'exo : Character et MateriaSource.

Pourquoi operator= d'AMateria ne copie pas le type ?

Si on fait monIce = unCure, l'objet reste un Ice. Lui donner le type "cure" n'aurait pas de sens. C'est l'astuce du sujet.

Qui libère la mémoire ?

  • Les modèles appris : le destructeur de MateriaSource.
  • Les Materias équipées : le destructeur de Character.
  • unequip ne fait pas delete (le sujet l'interdit). Le main garde l'adresse avant, puis fait delete.

Preuve : valgrind affiche 0 fuite.

Pourquoi class ICharacter; dans AMateria.hpp ?

AMateria.hpp et ICharacter.hpp parlent l'un de l'autre. S'ils s'incluaient tous les deux, ils tourneraient en rond. La déclaration anticipée dit juste « ce nom existe ». Le vrai #include est dans le .cpp.

Il y a des {} dans tes interfaces. La grille n'interdit pas le code dans les headers ?

Si, mais ces {} viennent du sujet : il impose virtual ~ICharacter() {}, et la grille demande des interfaces « exactement comme le sujet ». Toutes mes autres fonctions sont dans les .cpp.

  • delete la Materia appartient maintenant à me → son destructeur la libérera
tmp = src->createMateria("cure");
me->equip(tmp);
  • Même chose avec Cure → Cure::clone(), rangée dans le slot 1
  • tmp est réutilisé : il change juste d'adresse
ICharacter* bob = new Character("bob");
  • Un 2ᵉ personnage, il sert juste de cible. Son sac reste vide
  • delete fait par le main : delete bob;
me->use(0, *bob);
  • use(int, ICharacter&) = 0 dans ICharacter.hpp, codée dans Character.cpp. Vérifie l'index (0 à 3) et que le slot n'est pas vide
  • Puis appelle _inventory[0]->use(*bob) → Ice::use dans Ice.cpp (polymorphisme : le slot est un AMateria*, mais c'est la version d'Ice qui tourne)
  • Ice::use appelle getName() → codée dans Character.cpp → renvoie "bob"
  • *bob = l'objet bob lui-même, car use attend une référence
  • Affiche * shoots an ice bolt at bob *
me->use(1, *bob);
  • Pareil avec le slot 1 → Cure::use dans Cure.cpp
  • Affiche * heals bob's wounds *
delete bob;
  • Destructeur de Character, appelé via ICharacter* → marche grâce au destructeur virtual
  • Son sac est vide : rien d'autre à libérer
delete me;
  • Destructeur de Character → delete sur les 4 slots → libère l'Ice et le Cure équipés
  • Ces delete passent par AMateria* → le destructeur d'AMateria doit être virtual
delete src;
  • Destructeur de MateriaSource → delete sur les 4 modèles → libère l'Ice et le Cure appris

Le compte final

7 new dans ce main : MateriaSource, Ice (modèle), Cure (modèle), Character « me », Ice (clone), Cure (clone), Character « bob ».

7 delete : bob, me + ses 2 Materias, src + ses 2 modèles.

7 new = 7 delete, donc 0 fuite. C'est ce que valgrind doit confirmer. (Avec l'option B, il y a 2 clones de plus et 2 delete de plus dans learnMateria : le compte reste juste.)
